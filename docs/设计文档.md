# 1.12.2 模组兼容区块编辑器 · 设计方案

> 状态：**设计阶段（v0.3）**　|　目标版本：**Minecraft 1.12.2（Forge）**　|　定位：对标 MCA Selector 的区块操作 + 完整模组方块兼容
>
> **v0.2 变更**：GUI 方案更新为「游戏主菜单加按钮 → 进入 MCA Selector 式编辑器界面」（用户确认的方案，见 6.4）。
>
> **v0.3 变更**：阶段 0 格式实测完成（见 `report/格式验证报告.md`）——**1.12.2 存盘格式为 legacy 数组（Blocks/Add/Data），palette 仅内存/网络格式**；修正 §2.2/§3/§6 相关描述；确认 chunk 根级模组标签 / `ForgeDataVersion` / `Level.ForgeCaps` 需整份携带、region 头部第二表为时间戳（非 size 表）、无复数 Heightmaps；第 10 节清单 1–6、9 已实测。

## 0. 一句话结论（TL;DR）

你的两个痛点（预览显示错误、复制粘贴方块串模组）根因是同一个：

> **1.12.2 存档里的方块只存数字 ID，而存档本身不记录「数字 ID ↔ 方块名」的映射。** 这个映射只存在于「生成存档时在场的模组集合 + 模组加载顺序」里；而外部工具（MCA Selector 等）既没有这个映射，也没有模组方块的模型与渲染代码，所以预览错、粘贴串、替换失效。

因此推荐方案是：

> **以「游戏内 Forge 模组」为编辑核心**——注册表、方块模型、生物群系颜色、方块实体渲染全部由游戏本体提供，预览 100% 正确、操作 100% 语义正确。**交互形态：游戏主菜单加一个「区块编辑器」按钮，点击进入 MCA Selector 式的编辑器界面**——左上角选择存档、2D 区块地图、框选/删除/剪裁/复制/粘贴，操作手感与 MCA Selector 一致，同时模组方块全部正常显示（详见 6.4）；**外部伴侣工具**（可选）消费模组导出的「注册表快照 + 烘焙模型」做同样的浏览与批量操作。

## 1. 目标与范围

### 1.1 目标

1. 对 1.12.2 存档（Anvil / .mca 格式）提供 MCA Selector 同级的**区块级操作**：
   - 浏览 / 选择（按区块、按范围、按维度）
   - 删除（清空为虚空 / 从 region 文件移除）、剪裁（prune / trim，按半径或范围）
   - 复制、移动（同世界 / 跨世界 / 跨存档）
   - 导出、导入、统计、替换
2. **模组方块全程正确**：
   - 预览视图能正确显示模组方块（含地形/环境类模组新增的方块与生物群系）
   - 复制粘贴不串模组（方块、方块实体、实体、生物群系数据完整保留）
3. **跨存档/跨世界操作有明确的冲突检测与回退策略**：干跑（dry-run）报告、缺失方块回退配置、模组集合指纹比对。
4. 适配 1.12.2 原版与主流模组包（Biomes O' Plenty 之类的地形/环境模组作为验证基准）。

### 1.2 非目标

- 不支持 1.13+ 存档；不做存档版本升级/降级（DataFixer 类工作）。
- 不做地形生成（WorldGen）改造。
- 首期不做分布式/多线程批量编辑（预留接口即可）。

## 2. 问题根因分析

### 2.1 症状

| 症状 | 场景 | 表现 |
|---|---|---|
| 预览错误 | 外部工具打开含模组方块的存档 | 模组方块显示为紫黑块、空气或错误的原版方块；模组生物群系颜色错乱 |
| 方块串模组 | 区块复制粘贴（同存档或跨存档） | 模组 A 的方块变成模组 B 的方块，或变成不认识的方块 |
| 功能失效 | 替换/统计 | ReplaceBlocks 类操作对模组方块无效或写出错误方块 |

### 2.2 根因一：1.12.2 存档不自描述方块 ID

- 1.12.2 **存盘**用 legacy 数组：`Blocks`(byte[4096]) + `Add`(byte[2048] 半字节，方块 ID 高 4 位) + `Data`(byte[2048] 半字节，元数据)；**palette（int = 方块注册 ID << 4 | 元数据）只是 1.9+ 的内存/网络格式，1.13 起才写盘**（阶段 0 实测：约 14 万 chunk 无一含 Palette 标签，见 `report/格式验证报告.md`）。
- 方块注册 ID 由 Forge 启动时按「原版方块 → 各模组注册顺序」**依次分配**：原版约 380–400 个方块占 ID 0~约 390，模组方块从后面按加载顺序继续排（具体上界开发期在注册表实测）。
- **1.12.2 的 level.dat 里没有「ID ↔ 方块名」的注册表快照**（Registries 标签是 1.13 才加入的），存档里只有 `DataVersion: 1343`。
- 推论：同一个存档，**换模组集合或换加载顺序后，数字 ID 的含义就变了**。1.12 时代这个映射只能靠「生成存档时在场的模组集合」推断——这就是复制粘贴串模组的本质：源世界的 `1234:5` 被目标世界按自己的注册表解释成了另一个方块。

### 2.3 根因二：外部工具没有模组注册表与模型

- MCA Selector / Amulet / MCEdit 等外部工具内置的是**原版方块数据库与模型**。模组方块 ID 解析不出来 → 渲染成未知块；编辑时按错误 ID 写回 → 数据损坏。
- **外部渲染模组方块在原则上不可行**：Forge 的方块渲染走模组代码——`IStateMapper`、自定义 `ModelLoader`、OBJ/B3D 模型加载器、方块实体渲染器（TESR，如 AE2 终端、沉浸工程机器）。外部工具无法脱离模组代码还原这些方块的外观。

### 2.4 现有工具差距（含证据）

| 工具 | 类型 | 1.12.2 | 模组方块 | 备注 |
|---|---|---|---|---|
| MCA Selector 2.x | 外部，区块级 | 支持（1.12+） | **不支持**：未知渲染；ReplaceBlocks 对模组方块无效（[issue #480](https://github.com/Querz/mcaselector/issues/480)）；跨世界粘贴 MCA 文件有问题（[issue #521](https://github.com/Querz/mcaselector/issues/521)、[#532](https://github.com/Querz/mcaselector/issues/532)） | 基于 Amulet Core 读取存档 |
| Amulet Editor | 外部，方块级 | 支持（1.12+） | **不支持**：部分模组维度直接无法打开（[issue #922](https://github.com/Amulet-Team/Amulet-Map-Editor/issues/922)） | Amulet Core 对未知方块只能原样保留，无法编辑/渲染 |
| MCEdit Unified | 外部 | 1.12 支持残缺 | 仅旧式 mod block list | 已停更 |
| WorldEdit 6.x（模组） | 游戏内 | 支持 | 同一世界内 OK；剪贴板存数字 id+meta，**跨模组集粘贴会串** | 无区块文件级操作 |
| Litematica / Schematica（模组） | 游戏内 | 支持 | 游戏内渲染正确；但 1.12 原理图以数字状态 ID 为主，跨模组集转移同样会错（待实测确认内部格式） | 无区块级操作 |
| **本方案** | 游戏内核心 + 外部伴侣 | 支持 | **目标：完整支持** | 主菜单 MCA 式 GUI（见 6.4） |

## 3. 1.12.2 存档格式要点（数据基础速查卡）

> 开发期以「vanilla 1.12.2 客户端实测存档」为准逐条验证，见第 10 节待验证清单。

- **世界目录**：`region/r.x.z.mca`（32×32 区块；4KB 扇区；**头部 8KB = 1024×4B location 表（条目 = `(起始扇区 << 8) | 占用扇区数`）+ 1024×4B 时间戳表（不是 size 表！）**；chunk 数据 = 4B 长度 + 1B 压缩类型（1=gzip、2=zlib、3=none；实测全 zlib）+ NBT），`level.dat`（`DataVersion: 1343`）。
- **chunk NBT**：根 `{DataVersion: 1343, ForgeDataVersion, Level: {...}, <模组根级标签...>}`（Level 包裹层，1.13 起摊平）。**复制/移动时必须整份携带根级与 Level 内所有标签**（含模组数据标签如 `cofhworld`/`forestry`/`Thaumcraft`/`MekanismWorldGen` 与 `Level.ForgeCaps`），只重映射数字 ID。
- **Level 内关键字段**：
  - `xPos` / `zPos`：区块坐标
  - `Biomes`：`byte[256]`，每列一个**生物群系数字 ID（0–255）——同样存在模组冲突问题**
  - `Sections`：见下
  - `TileEntities`：列表，每条含 `id`（**1.11+ 已名称化**，如 `minecraft:furnace`、`modid:xxx`，无 ID 冲突）、`x/y/z`、其余自定义 NBT
  - `Entities`：同，`id` 为名称化字符串（实测如 `battletowers:golem`）
  - `HeightMap`（旧式，`int[256]`）实测存在；**复数 `Heightmaps` 实测不存在**（1.13 才有）；编辑后由游戏重建
- **Section（Y 层）——实测（1.12.2 存盘 = legacy 数组）**：
  - `Y`：层高字节
  - `Blocks`：`byte[4096]`，方块 ID 低 8 位；索引 `y*256 + z*16 + x`
  - `Add`：`byte[2048]` 半字节，方块 ID 高 4 位（**存在 id>255 的方块时出现**，实测 `363:5` 等）；半字节顺序同 Data
  - `Data`：`byte[2048]` 半字节，元数据 0–15；**x 偶 → 低半字节，x 奇 → 高半字节**（NibbleArray 语义，实测 7=基岩/1=石头/9=水/168=海晶石吻合）
  - `BlockLight` / `SkyLight`：`byte[2048]`（半字节）
  - **兼容读取**：部分工具/写入器可能输出 `Palette`(int[]，条目=`blockId<<4|meta`) + `BlockStates`(long[] 位压缩：每方块 `max(4,ceil(log2(n)))` 位、索引 `y<<8|z<<4|x`、低位在前跨 long)——1.13 的存盘形态，1.12 不产生，但读取端保留兼容（自造样本已验证解码正确）
- **光照**：随 section 存储。区块整体移动时自带光照自洽；**改动方块后必须处理光照重算**（文件级操作需内置 relight 或标记重建，见 6.3）。

## 4. 方案选型

### 4.1 方案 A：纯外部工具（扩展 MCA Selector 思路）

- 优点：不启动游戏、批处理快、无模组加载负担。
- 死穴：
  1. **注册表**：外部工具拿不到模组注册表，只能靠「模组内手动导出快照」逐存档维护，且用户易忘、易错；
  2. **渲染**：模组方块模型依赖模组代码（自定义 ModelLoader / TESR），外部只能退化为「导出的烘焙贴图 / 彩色盒子 / 紫色未知块」，体验远差于游戏内；
  3. 开发量巨大（要重写半套渲染器），收益却有限。
- 结论：**不作核心**，只作伴侣工具（见 4.3）。

### 4.2 方案 B：游戏内 Forge 模组（推荐核心）

- 优点：
  - **注册表天然完整**：`Block.REGISTRY` / `Biome.REGISTRY` / `TileEntity` 注册表 / 实体注册表全部在场，`modid:block` ↔ 数字 ID 双向映射直接可得；
  - **渲染天然正确**：2D 地图取色/渲染直接使用游戏自己的模型管线（`IBakedModel` / `BlockRendererDispatcher`），模组方块 100% 正确，无需任何模型数据库；
  - **语义天然正确**：通过 `World.setBlockState` / `Chunk` API 操作，方块更新、光照、高度图由游戏处理；
  - **可无头批量**：用 `MinecraftServer` 引导（headless）加载世界，做文件级批量操作（删除/剪裁/统计），兼顾批处理场景；
  - **可导出数据**：向伴侣工具导出注册表快照、生物群系颜色表、烘焙模型。
- 缺点：操作时需启动游戏（可用专用编辑客户端/实例缓解）；大模组包启动慢（可接受）。

### 4.3 方案 C：混合架构（推荐整体方案）

| 组件 | 职责 | 关键技术 |
|---|---|---|
| **游戏内模组（核心）** | 主菜单 MCA 式编辑器（区块级）+ 方块级编辑、跨世界重映射、快照导出 | Forge 1.12.2，见第 5、6.4 章 |
| **外部伴侣工具（可选，后期）** | 同样的 2D 地图浏览、批量删除/剪裁（**不需要理解方块语义的操作对模组方块天然安全**）、任务队列 | Java + JavaFX；消费模组导出的快照/模型 |
| **数据桥** | registry-snapshot.json、biome-colors.json、烘焙模型包 | 见 5.4 |

> 关键设计点：**「需要理解方块语义」的操作一律放游戏内；「不需要理解方块语义」的操作（整块删除/剪裁/移动）外部工具也能安全做。** 这是把开发难度和正确性同时控制住的分界线。

### 5.1 架构图

```
┌─────────────────────────────────────────────────────────────────┐
│                    游戏内 Forge 模组（编辑核心）                    │

│                    冲突策略、干跑报告                              │
│  chunkops-ops      操作引擎：删除/剪裁/移动/复制/替换/统计          │
│                    └─ 文件模式（直接读写 region，主菜单编辑器用）   │
│  chunkops-gui      主菜单 MCA 式编辑器：存档选择/2D 地图/          │
│                    框选/操作面板/任务队列/日志（见 6.4）           │
│  chunkops-export   注册表快照、biome 颜色、烘焙模型、.mcops 导出    │
│  chunkops-server   （可选）预览渲染服务 / 远程控制                 │
└──────────────┬──────────────────────────────────┬───────────────┘
               │ 导出快照/模型/.mcops               │ 预览请求
               ▼                                   ▼
┌──────────────────────────────┐   ┌──────────────────────────────┐
│  外部伴侣工具（后期可选）        │   │  游戏渲染管线（2D 地图取色/     │
│  2D 地图 / 批量删除剪裁 / 统计   │   │  渲染，模组方块 100% 正确）     │
└──────────────────────────────┘   └──────────────────────────────┘
```

### 5.2 模组端模块划分（Forge 1.12.2）

- `chunkops-core`：NBT 工具、MCA 区域文件读写、Section 解码器（legacy 数组为主 + palette 兼容）、canonical 区块中间表示（名称化）、Lighting 重算（策略接口）。
- `chunkops-remap`：`RegistrySnapshot` 加载/校验、`NameIdBiMap` 双向映射、`RemapPipeline`（第 6.2 节）、`ConflictReport`、回退策略配置。
- `chunkops-ops`：区块级与方块级操作实现；**主菜单编辑器走「文件模式」**（直接读写磁盘 region，不加载世界进内存，大存档流畅），必要时可配合无头服务器过一遍（收尾校验）；
- `chunkops-gui`：**主菜单 MCA 式编辑器界面**（存档下拉选择、2D 区块地图、框选、右键菜单、操作面板、任务队列、进度与日志、干跑报告展示；详见 6.4）。
- `chunkops-export`：快照/模型/原理图导出。
- `chunkops-server`（可选）：内嵌 HTTP 服务，供伴侣工具请求「指定区域预览图」（由游戏真实渲染，彻底绕开外部渲染问题）。

### 5.3 伴侣工具模块（阶段 4，可选）

- 2D 地图视图（对齐 MCA Selector 交互）：区块网格、选择、批量删除/剪裁、统计报表；
- 方块渲染：优先用模组导出的烘焙模型包；缺失时退化为「按方块名哈希取色 + 紫色未知块标记」；
- 加载 `registry-snapshot.json` 后，可安全执行「不需要理解方块语义」的操作。

### 5.4 数据文件规范

**registry-snapshot.json**（模组导出，放在存档目录或用户指定位置）：

```jsonc
{
  "formatVersion": 1,
  "gameVersion": "1.12.2",
  "dataVersion": 1343,
  "fingerprint": "sha256(排序后的 modid:version 列表)",
  "mods": [ { "modid": "biomesoplenty", "version": "7.0.1" }, ... ],
  "blocks": [ { "name": "modid:blockname", "id": 1234 }, ... ],   // 含原版
  "biomes": [ { "name": "modid:biomename", "id": 200 }, ... ],
  "generatedBy": "chunkops-export"
}
```

- `fingerprint` 用于**跨存档操作前警告「模组集合不一致」**，这是 1.12.2 环境下最重要的安全网。
- 方块以 `id` 为键、名称为值；编辑器解析 palette 时用它把 `id<<4|meta` 还原成 `modid:block + meta`。

**.mcops（自有原理图/剪贴板格式，gzip NBT）**：

```text
{
  Format: 1, Kind: "chunks" | "area", DataVersion: 1343,
  Source: { fingerprint, note },
  Origin: [x, z], Size: [w, h, d],
  Palette: [ "modid:block#meta", ... ],        // 名称化 palette，天然跨世界可移植
  Blocks: [paletteIndex, ...],                 // 逐方块索引
  TileEntities: [...], Entities: [...],        // 原样 NBT
  Biomes: [ "modid:biomename", ... ]
}
```

- 关键约定：**一切跨世界转移必经重映射管线**（第 6.2 节），任何输入（MCA 文件、.mcops、编辑器剪贴板）先规范化成名称化表示，再落到目标注册表。

## 6. 核心机制设计

### 6.1 统一方块表示 BlockRef

```text
BlockRef = { name: "modid:block", meta: 0–15, tileEntity: NBTTagCompound? }
解析管线：stateId(int) → (blockId, meta) → 快照/活注册表查名 → BlockRef
未知方块：保留为 "unknown:<id>:<meta>" 占位并计数，全程不丢信息（可导出报告）
```

- 主菜单编辑器直接用 `Block.getStateId(IBlockState)` 与 `Block.REGISTRY` 反查，无需快照；伴侣工具用快照。
- 方块实体 NBT **原样携带**（目标端只校验 `id` 字段是否存在，不解析内部结构——各模组 TE 数据格式互不通用，动它必坏）。

### 6.2 复制粘贴 / 跨世界重映射管线（8 步）

1. **读源**：文件模式读 region/chunk NBT；
2. **解码**：逐 section 解 legacy 数组（Blocks/Add/Data，NibbleArray 半字节顺序）或 palette+BlockStates（兼容路径）→ `BlockRef` 列表（活注册表/源快照）；
3. **规范化**：重建成名称化 palette（此时已与源存档的 ID 分配无关）；
4. **查目标**：在目标活注册表/目标快照中查 `modid:block` → 目标 stateId；
5. **重建**：按目标 palette 重算位宽（`max(4, ceil(log2(n)))`），重建 BlockStates long 数组；
6. **方块实体/实体**：NBT 原样携带，校验 `id` 在目标注册表存在，缺失走策略；
7. **生物群系**：按名称重映射（源 biome 名 → 目标 biome ID），缺失走策略；
8. **输出**：整份 chunk NBT 写入目标（**根级与 Level 内所有标签原样保留，含模组数据标签与 `ForgeCaps`**）+ 生成 `ConflictReport`（方块名、数量、处理动作）；**干跑模式只出报告不写入**。

**冲突策略（可配置）**：

| 策略 | 行为 |
|---|---|
| `fallback`（默认） | 缺失方块 → 可配置回退（air / 石头 / 屏障占位），报告里列全 |
| `abort` | 任一冲突即中止，不写入任何数据 |
| `keep-raw`（危险） | 保留原始数字 ID 并打标记（仅供同模组集世界使用） |

- 支持按方块名配置白名单/黑名单（如「只迁移模组 X 的方块，其余回退」）。
- **跨世界粘贴前必做指纹比对**：源快照 fingerprint ≠ 目标快照 fingerprint → 明确警告并默认进入干跑。

### 6.3 区块级操作与光照/高度图策略

| 操作 | 语义 | 光照/高度图处理 |
|---|---|---|
| 删除（清空） | 区块方块全清为虚空，保留区块结构 | 光照数组清零 + 标记重建 |
| 删除（移除） | 从 region 文件移除该区块记录（重写索引） | 无（不涉及方块数据） |
| 剪裁 prune/trim | 按半径/范围批量删除区块 | 同「移除」 |
| 复制/移动区块 | 区块 NBT 整体走重映射管线 | **整块移动自带光照自洽**（区块自带 BlockLight/SkyLight）；边界接缝用 relight 收尾（可选） |
| 替换/过滤 | 方块级，按名称/正则 | 改动后 relight |

- 主菜单编辑器（文件模式）的光照处理：
  1. 内置 relight（移植 1.12 的方块/天空光传播算法，参考 MCEdit Unified / Amulet Core 的实现）；
  2. 或「无头服务器过一遍」：操作完后，用本模组启动的 headless MinecraftServer 加载受影响区块触发重算再保存（准确但慢，适合收尾校验）。
- 首期策略：**删除/剪裁/整块移动不碰方块语义，无需 relight**；方块级改动（替换）走文件级写入 + 光照标记重建，把 relight 问题推迟到阶段 2/3 再彻底解决。

### 6.4 编辑器界面与 2D 地图渲染（主菜单 MCA 式，v0.2 确认方案）

**交互形态（对标 MCA Selector）**：

- 游戏主菜单（`GuiMainMenu`）增加一个「区块编辑器」按钮 → 点击进入编辑器界面；
- 左上角**存档下拉选择**：列出 Saves 目录中的世界（世界名 / 最后游玩时间 / 图标），支持维度切换（主世界 / DIM1 / DIM-1）；
- 主区域 = **2D 区块地图**：俯视、区块网格线、坐标显示、缩放、高度着色（与 MCA Selector 观感一致）；
- 操作方式：鼠标**框选区块/区域** → 右键菜单（删除 / 剪裁 / 复制 / 粘贴 / 导出 / 统计 / 替换）→ **干跑报告弹窗** → 确认写入；复制后可切换到另一个存档再粘贴（跨世界自动走 6.2 重映射管线）；
- 底部任务队列：进度条、日志、冲突报告入口；
- 回到主菜单按钮、只读浏览模式开关。

**渲染策略（关键：不把世界加载进内存，只借游戏的渲染能力）**：

1. **数据源**：直接读 `saves/<world>/region/*.mca`（及维度目录），解析 chunk NBT → legacy 数组/palette 经**活注册表**转方块名（天然兼容模组，无需任何外部数据库）；
2. **地表取列**：优先读旧式 `HeightMap`（int[256]）得到每列地表 Y；缺失/异常时从 y=255 向下扫描取第一个非空气方块；
3. **取色（首期实现）**：对地表方块取 `IBakedModel` **朝上 quad** 的 `TextureAtlasSprite` 中心像素色，叠加高度明暗（MCA 同款观感）；无顶面 quad 的方块（如横放的机器）回退其他面或 `getMapColor()`；**「方块名→颜色」全局 LRU 缓存**，浏览实时无压力；
4. **增强（后期）**：离屏 FBO 正交渲染区块顶面（`BlockRendererDispatcher`），得到真实光影的「照片级」地图；
5. **异步与缓存**：工作线程池负责加载/解析/渲染，主线程只贴图；LRU 地图缓存 + 可选磁盘缓存，几万区块的大存档也流畅；
6. **生物群系颜色**：用活注册表 `Biome.REGISTRY` 按名取色（含模组生物群系），替代 MCA 的原版色表。

**主菜单按钮注入**：Forge `GuiScreenEvent.InitGuiEvent.Post` 添加按钮 + `GuiScreenEvent.ActionPerformedEvent` 处理点击（社区成熟做法）；若事件方案有兼容性问题，备选 Mixin 注入 `GuiMainMenu`（开发期验证，见第 10 节）。

**安全**：打开存档前检测 `session.lock`（该存档正被另一游戏实例占用时警告，防止双写损坏）；写入前自动备份；干跑先行（同 6.5）。

### 6.5 操作安全

- 操作前**自动备份**（`.mcabackup`，按 world 目录整体或按 region 文件）；
- **只读模式**（浏览/统计/干跑不落盘）；
- **干跑报告**先于真实写入；
- **存档占用检测**：编辑前检查 `session.lock`，另一实例占用时拒绝写入并提示；
- 文件级撤销 = 备份回滚。

### 6.6 精确数据层：Xaero 式游戏内采集（增强方案，v0.4）

**动机**：文件级显示的取色（`IBakedModel` 纹理中心采样）对部分模组方块不稳（横放模型、多层模型、无帧数据的 sprite）；参考 Xaero World Map 的成熟机制——**在游戏运行时用「地图颜色语义」取色并缓存**，显示 100% 正确。

**Xaero 的取色机制（实测数据目录 + 社区实现）**：

- 数据文件：`xaero/world-map/<世界>/<维度>/cache_16/<rx>_<rz>.xwmc`（私有 RLE 压缩，存颜色+高度；`.outdated` 后缀=过期待重采；主世界维度目录名为 `null`）
- 取色栈（游戏内，对已加载 chunk 逐列）：
  1. **地表方块**：`world.getBlockState(pos)`（游戏内 world 对象，地表判断天然准确）
  2. **基础色**：`state.getMapColor(world, pos)`——vanilla 地图色系统（MapColor：石头=灰、草=GRASS 绿、水=蓝；支持草皮/水等图层叠加）
  3. **生物群系色调**：`Minecraft.getMinecraft().getBlockColors().colorMultiplier(state, world, pos)`——与游戏渲染同源的方块色调 Provider（草/叶/水按生物群系调色，模组可注入自己的 Provider）
  4. **高度明暗**：渐变观感（MCA/Xaero 的"丰富感"来源）
  5. 写入缓存（Xaero 仅存颜色+高度）

**我们的设计（自研格式，能力更强）**：

- 数据文件：`chunkops/map/<世界名>/<维度>/<rx>_<rz>.dat`
  - 头部：魔数 `COPM`、版本、尺寸（256×256 列 = 1 region）
  - 字典：方块名 `modid:block#meta` 列表 + 生物群系名列表
  - 每列 RLE 数据：颜色 ARGB(4B) + 高度(1B) + 方块名索引(2B) + 生物群系名索引(1B) ≈ 8B/列（RLE 后显著更小）
- **采集时机**：游戏内玩家探索时增量（chunk 加载事件触发，后台线程采集，不卡帧）——采到的颜色/方块名/生物群系名全部来自游戏运行时（活注册表 + BlockColors），**不需要任何取色猜测**
- **编辑器显示（双层）**：
  - 第一层（精确）：有数据文件的块 → 直接用采集颜色（含生物群系调色），DynamicTexture 显示
  - 第二层（回退）：无数据块 → 现有文件级 region + HeightMap/取色（至少看到轮廓；新装模组/未探索区域不空白）
- **操作层不受影响**：区块操作仍走文件级，与显示层解耦
- **编辑器额外能力**：基于方块名索引可做统计/替换/过滤（比 Xaero 多出的能力）
- 文件级回退层的取色策略修正为 `getMapColor(state, null, pos)`（MCA Selector 同款语义色），不再依赖纹理采样

**取舍**：
- 数据是「玩家探索视角」：未探索区域靠回退层显示；统计仅覆盖探索过的区域
- **不做**：不逆向 `.xwmc`（私有格式 + 版本风险，且不含方块名）
- 规划：阶段 3 验收后作为 **P2 增强项**实施

> **实施状态（2026-09-01 v1 已落地，提交 37c77da）**：
> - 采集器 `ExactMapCollector`（`ChunkEvent.Load` 即时 + `ClientTickEvent` 每 40 tick 扫描兜底双路径；2 个 daemon 后台线程；仅单人世界；防重集合 + region 文件锁合并写）——取色栈实现：`state.getMapColor(world,pos)` × `BlockColors.colorMultiplier(st,world,pos,0)` + `MapColorCache.shade` 高度明暗；
> - 格式 `ExactMapFile`（COPM v1：魔数 "COPM"+版本+GZIP；内部 u16 尺寸 + 双字典（block/biome name，`modid:block#meta`）+ 列 RLE（varint count + 4B 色 + 1B 高 + 2B 块索引 + 1B 群系索引）；空白/虚空列约定 blockIdx=0&&height=0&&color=0；原子写 tmp+rename；round-trip 测试通过）；
> - 路径 `gameDir/chunkops/map/<世界名>/<dim>/r.<rx>.<rz>.dat`（世界名取自集成服务器 WorldServer 的 saveHandler 目录名，与编辑器读 `saves/<名>` 对齐）；
> - 编辑器双层显示：`ChunkMapRenderer` 精确层优先（region LRU 64，线程安全），数据列缺失自动回退文件级取色；状态栏显示「精确层 N 列」；
> - 待验证：真实游戏采集效果（进 GreedyCraft 跑图 → 检查 map 目录文件生成 + 编辑器精确列着色）。

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| 存档损坏（写坏 MCA / NBT） | 操作前自动备份；原子写（先写临时文件再替换）；只读模式；干跑先行；session.lock 占用检测 |
| 模组集合变化导致 ID 漂移 | 注册表快照 + fingerprint 比对警告；一切操作以名称为准，数字 ID 只在最终落盘时使用 |
| 光照接缝/黑块（文件级改块后） | 整块移动自带光照；方块级改动走光照标记重建 + relight（阶段 2/3） |
| 大模组包性能（几百模组启动/操作慢） | 地图渲染全异步 + LRU/磁盘缓存；文件级操作不加载世界，浏览不占大内存 |
| 1.12.2 工具链老旧（FG2.3 只认 JDK8/Gradle 4.x） | 固定开发环境（独立 JDK8 + 固定 Gradle 版本），README 写明安装步骤 |
| DataVersion 非 1343 的存档 | 读取前校验，不匹配拒绝操作并提示 |
| 方块实体/实体 NBT 不兼容 | 原样保留 + 只校验 id 存在性；报告未知项 |
| 模组方块渲染导出不完整（TESR 等） | 主菜单编辑器始终可看（游戏内渲染）；伴侣工具明确标注「外部不可渲染」清单 |
| 2D 地图取色与真实观感差异 | 取色走真实纹理（IBakedModel + atlas），非猜测色；后期提供真实光影渲染模式 |
