## 8. CI / 发布（2026-09-16 加入）

- **Gradle wrapper**：仓库自带 `gradlew` / `gradlew.bat` + `gradle/wrapper/`（**固定 Gradle 4.9**，ForgeGradle 2.3 的限制）。本机与 CI 都用它：`./gradlew build`（Win：`gradlew.bat build`）；仍需 **JDK 8**（`JAVA_HOME` 指向 JDK8）。
- **`.github/workflows/build.yml`**：push 到 `main` / PR / 手动触发 → JDK 8 + Gradle 4.9 构建 → jar 作为 Artifact 上传。含 **3 次重试**（libraries.minecraft.net / MCP 下载偶发失败）与 `~/.gradle` 缓存。
- **`.github/workflows/release.yml`**：推送 `v*` 标签（或手动运行并填标签）→ 构建 → **校验版本一致性**（标签去掉 `v` 必须等于 `build.gradle` 的 `version` 与 `ChunkOpsMod.VERSION`，不一致直接失败）→ `softprops/action-gh-release` 创建 Release 并上传 `chunkops-<版本>-mc1.12.2.jar`（`generate_release_notes: true` 自动生成更新日志）。权限用 `permissions: contents: write`，**无需自配密钥**（Actions 自带 `GITHUB_TOKEN`）。
- **`.gitattributes`**：统一 LF（`*.bat` 用 CRLF、二进制不转换），保证 Linux CI 与 Windows 一致；`gradlew` 已用 `git update-index --chmod=+x` 标记可执行位。
- **发版流程**：改两处版本号 → 提交 → `git tag vX.Y.Z && git push origin main && git push origin vX.Y.Z`。
- 注意：沙箱里 `services.gradle.org` 与 `github.com` 不通，**wrapper 首次下载与 push 都需在用户本机/CI 上做**（本机验证 wrapper 时是把 `C:\Gradle\gradle-4.9` 手动塞进 `GRADLE_USER_HOME/wrapper/dists/` 完成的）。

## 9. 注册表编号漂移修复（阶段 A+B，2026-09-17）

**问题**：1.12.2 存档里的方块只有数字（stateId = registryId<<4|meta），含义由**当前会话**的 `Block.BLOCK_STATE_IDS`（每次启动按注册顺序重建）决定；mods 目录一变 → 注册顺序变 → 同一个数字被解释成别的方块。**游戏无从知道**旧含义（1.13 的 Flattening 才把方块名写进存档）。物品/实体/方块实体在 1.12.2 存的是**名字**，所以只有「世界里的方块」会坏。

**方案（已实现）**：
- **A-1 快照留档**：`ChunkOpsExport` 除写 `registry-snapshot.json` 外，另写 `registry-snapshot.hash`（编号映射指纹）；`SnapshotStore.archiveFile()` 把每份**不同内容**的快照归档到 `<gameDir>/chunkops/snapshots/<时间戳>-<hash8>.json`（同内容不重复归档，幂等）。
- **A-2 世界指纹**：`<存档目录>/chunkops/registry-at-write.json`（**几百字节的小文件**，只存 `mappingHash` + 归档快照文件名 + 时间，不复制整份快照）。编辑器选中存档时：没有指纹 → 记基线；有且与当前会话不一致 → 顶部红标 **⚠ 编号已漂移** + 日志警告。写盘操作后刷新指纹，**漂移时故意不刷新**（保住旧指纹，修复才有依据）。
- **B 一键修复**：`RegistryRepair` 用两张快照按 `name#meta` 对齐 → **JEID 世界只原地改写 section 的 `Palette int[]`**（方块本体是 palette 索引，Blocks/Data/光照都不动，几万区块几秒）；legacy 世界才解码 4096 项重建（保留 Y 与光照）。默认 dry-run；apply 时每 region 由 `RegionWriter` 自动 `.mcabackup` + 原子写，写后**回读校验**，并报告「当前注册表已不存在的方块项」（保留原值）。GUI：`ChunkOpsRepairScreen`（编辑器右上「修复编号」，两步确认防误操作，后台线程跑）。
- **stateId 0（空气）恒定不参与重映射**（防御性）。

**离线验证（真实数据）**：
- `tools/verifier` 新增 `RegistryRepairTool`（drift/scan/apply/shift/names）与 `SnapshotStoreCheck`。
- **legacy 路径**：Cleanroom 真实存档 7 region → `scan` 认出 1127 区块需改；apply 后按「新快照」解码 r.0.0.mca = **449150 方块 / 21 种，与修复前按旧快照解码完全一致**；再反向修复一次 → 往返一致（语义零损失）。
- **JEID 路径**：GreedyCraft `地图`（587 模组环境）+ 真实 15.6 MB 快照 → `palette 项 65780 → 改写 65095`、legacy 0、547 区块，apply 后按新快照解码 **31890 方块 / 7 种，与修复前一致**；用时 1.6 s。
- **哈希一致性**：`SnapshotStoreCheck` 验证「导出器算法（读原始 JSON 顺序）」与「core 算法（读已加载快照）」在两份真实快照（3913 / 203115 条）上**逐字节一致**——不一致会导致误报漂移。归档幂等、世界指纹读写/解析、漂移可检出均通过（退出码 0）。

**限制（务必向用户说明）**：只能修「有当时快照」的存档（从现在起自动留档）；**此前已坏且无快照的数据无解**；已被卸载模组的方块无法映射（保留原值并列出）。
